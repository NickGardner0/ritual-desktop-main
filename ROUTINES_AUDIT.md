# Routines rebuild — Phase 0 audit

## Stack

- **Frontend**: Next.js App Router (`apps/dashboard`), rendered inside a Tauri desktop shell (`apps/desktop`). React 18, TanStack Query for server state, Clerk auth, Tailwind + shadcn/radix primitives (`components/ui/*`), `sonner` toasts, `lucide-react` icons.
- **Backend**: FastAPI (`apps/backend`) over Turso/SQLite (SQLAlchemy). The dashboard proxies `/api/*` to the backend (`proxy.ts`); reads/writes go through `apiJsonWithAuth`.
- **AI plumbing**: real and working. Backend `workflow_service` queues `workflow_runs`, a 5-minute `workflow_scheduler_loop` (`background_tasks.py`) POSTs each queued run to the dashboard's `/api/internal/workflows/execute`, which runs `lib/workflows/executor.ts` (OpenAI `gpt-4o-mini`, deterministic fallback when OpenAI is unavailable) and returns an **artifact** — the Reports system's native object.
- **Reports**: `/reports` renders artifacts (`/api/artifacts`), opens a specific one via `/reports?artifactId=…`. Workflow runs carry `artifact_id`.
- **Tests**: `node --test apps/dashboard/tests/*.test.mjs`; pure logic modules are authored as `.mjs` (e.g. `lib/ai/overview-activity/weekly-overview-utils.mjs`) so tests import them directly.
- **Repo guardrails**: 800-line budget per dashboard `.ts/.tsx` file; no direct backend fetches (use `apiJsonWithAuth`); dead-code and import-cycle checks.

## Existing Routines feature

- Page: `app/(dashboard)/routines/{page,routines-client}.tsx` — master-detail (list sidebar + editor panel), `Mine / Templates / Runs` tabs, form-style editor exposing raw fields (kind, trigger, task template…). This is the surface being replaced.
- Data model (backend `database/models/tasks.py`, mirrored in `lib/tasks/types.ts`): `routines`, `routine_runs`, `tasks`. Routines already have `trigger_type` (`daily|weekly|monthly|yearly|on_completion`), free-form `trigger_config` JSON, `timezone`, `first_run_at`, `ends_at`, `last_run_at`, `next_run_at`, `status` (`draft|scheduled|paused|archived`), and `ai_workflow_definition_id` linking to a workflow definition.
- Endpoints: `GET/POST /api/routines`, `PATCH /api/routines/{id}` (no DELETE — archive via status), `GET /api/routines/runs`, `POST /api/routines/preview`, `POST /api/routines/generate-due`. Workflows: `GET/POST/PATCH /api/workflows/definitions`, `POST /api/workflows/definitions/{id}/run` (manual run, processed immediately), `GET /api/workflows/runs[?definition_id]`, `GET /api/workflows/runs/{id}`.
- Recurrence engines exist twice: backend `services/recurrence.py` and frontend `lib/tasks/recurrence.ts` (`nextRoutineDates`, `summarizeRecurrence`). Weekday convention is **0 = Monday**. Month-end clamping already handled; descriptions lack the time component.
- Local-first: routines/tasks are mirrored to a local vault with a write outbox (`lib/privacy/task-vault-adapter.ts`, `use-task-routine-outbox-sync`). New UI keeps using these helpers.
- Design idiom for this surface: `lib/tasks/reference-task-shell.tsx` (ReferencePage/Header, SegmentedTabs, FieldGroup/FieldRow, IconButton, control classes). Palette on the Tasks/Routines surface is the light `#f7f8f5`/`var(--content-bg)` family with `#167046` (success) and `#b45309` (warning) already in use as status colors. Global tokens live in `app/globals.css` (`--surface-*`, `--text-*`, `--radius-*`). Radix `Dialog`, `DropdownMenu`, `Popover`, `Switch`, `Tooltip` are available.

## Plan → codebase mapping (deviations)

1. **No new tables.** The plan's `Routine` maps onto the existing model: `name→title`, `instructions→description`, `schedule→trigger_type + trigger_config + timezone + first_run_at/ends_at`, `paused→status ('scheduled'|'paused')`, `nextRunAt→next_run_at`. New agent fields (`agentTier`, `notifyPush`, `notifyEmail`, `dataSources`, `icon`, `templateId`) live under **`trigger_config.agent`** on the routine (free-form JSON, no schema migration). *Discovered constraint:* `workflow_definitions` has a UNIQUE index on `(user_id, kind)` in the production Turso DB, so per-routine definitions are impossible without a migration — routines instead share the per-kind default definition and carry their own agent config into each run.
2. **Every routine created by the new UI is an AI routine** (`kind: 'ai_workflow'`) pointing at the shared per-kind workflow definition. The **routine** is the single source of scheduling truth: `generate-due` queues the workflow run with the routine's agent config copied into the run's `plan_json` (`{routine_id, config_override}`), and `workflow_service._process_run` merges that override into the config delivered to the executor. A new `POST /api/routines/{id}/run-now` endpoint queues a manual run the same way (recording a `routine_runs` row for attribution) and processes it immediately.
3. **`scheduleEngine`** = a new pure `.mjs` module (`lib/routines/schedule-engine.mjs`) superseding `lib/tasks/recurrence.ts` for this surface: `nextOccurrences()` + `describeSchedule()` with time-of-day in descriptions, `firstRun`/`ends`, intervals, month-end clamping, DST-safe local math, exhaustive `node --test` coverage. Existing `trigger_config` conventions are kept (`interval/hour/minute/weekdays/day/month/mode`, weekdays 0=Mon).
4. **Runs**: `routine_runs` rows are the source of attribution (one per scheduled or manual occurrence, including `skipped` catch-up markers), joined client-side with `/api/workflows/runs` by `workflow_run_id` for live status, artifact link, duration, and manual/scheduled trigger. "Open report" navigates to `/reports?artifactId=…`.
5. **Scheduler**: reuse the plan's shape with existing infra — a client hook fires `POST /api/routines/generate-due` on page load and each minute (idempotent); the backend 5-minute workflow loop executes queued AI runs. **Backend change (contained, no migration)**: `generate_due_routines` gains catch-up semantics — when multiple occurrences were missed, record older ones as `skipped` runs and generate only the most recent, then advance `next_run_at` strictly into the future (today it walks one occurrence per call, which would trickle-stampede).
6. **"Run now"** = `POST /api/workflows/definitions/{id}/run` — processed immediately server-side, so a run row appears at once (queued → processing → completed).
7. **Executor**: instead of a `MockExecutor`, extend the real `lib/workflows/executor.ts`: when `config.instructions` is present it collects data per `config.data_sources` + `config.agent_tier` and synthesizes with the user's instructions in the prompt; the existing deterministic fallback covers no-OpenAI environments (this *is* the mock path, fed by real aggregates). No backend enum changes — custom routines reuse the `daily_narrative` kind and branch on `config.instructions`.
8. **Notifications**: workflow delivery channel is `in_app` only. The Push toggle stores `notify_push` and fires a Web Notification (with permission) when the client observes a run complete; the Email toggle renders disabled with a tooltip naming the fix, since no email channel exists for workflows yet.
9. **Dictation**: mic affordance skipped (plan marks it optional); no shared dictation component on this surface.
10. **Templates**: replace `AI_ROUTINE_TEMPLATES` with the plan's 7 Ritual-domain templates (categories Suggested/Sleep/Fitness/Focus/Reading/Coding/Reviews), each with first-person instructions, data-source icons, and default schedules. "Anomaly Watch"'s only-if-notable behavior is expressed in its instructions (the executor always writes a run; a quiet "nothing notable" report is acceptable v1).
11. **Layout**: keep the page's master-detail pattern for Mine (rich rows left, detail panel right — matches the dark-app reference and the existing codebase pattern); Templates and Runs tabs use the full content width; empty Mine renders the hero + library. The Configure modal is a Radix Dialog.
12. **File layout**: new UI split across `app/(dashboard)/routines/*` + `lib/routines/*` to respect the 800-line budget.
